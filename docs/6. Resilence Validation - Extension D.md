# Extension D — Resilience Validation

## Objective

Validate that the Greeter service remains available during common Kubernetes disruption scenarios.

This extension tests the application under continuous client traffic while:

1. Draining one Kubernetes worker node.
2. Restoring the drained worker node.
3. Performing a rolling application update.
4. Observing request success and latency throughout the disruption.

The purpose is not only to demonstrate that Kubernetes eventually recovers, but also to measure what happens to real client requests while the disruption is occurring.

The exercise specifically requires evidence from a worker-node drain and a rolling update while requests are continuously sent to the service.

---

# 1. Architecture

The production environment runs two Greeter replicas across two worker nodes:

```text
                  Envoy Gateway
                       │
                       ▼
               greeter-prod Service
                       │
               ┌───────┴───────┐
               │               │
               ▼               ▼
          Greeter Pod 1    Greeter Pod 2
               │               │
               ▼               ▼
            Worker 0         Worker 1
```

The resilience configuration already implemented in the Helm chart includes:

```text
Multiple replicas
Topology spreading
Readiness probes
Liveness probes
PodDisruptionBudget
RollingUpdate strategy
Graceful SIGTERM handling
Termination grace period
```

The tests in this extension validate that these mechanisms work together correctly.

# 5. Request Evidence

Every request is recorded in CSV format:

```text
timestamp,http_code,time_total,result
```

Example:

```text
2026-08-27T14:10:00.123Z,200,0.004321,success
2026-08-27T14:10:00.241Z,200,0.003815,success
2026-08-27T14:10:00.359Z,200,0.004102,success
```

Each request records:

- UTC timestamp
- HTTP response code
- total request latency
- success or failure

A response is considered successful when the HTTP status code is in the `2xx` range.

Other responses are recorded as failures.

Connection failures are represented as:

```text
000
```

This makes short availability interruptions visible even if Kubernetes subsequently recovers.

# 7. Graceful Load-Test Termination

The load generator handles:

```text
SIGINT
SIGTERM
EXIT
```

and generates the summary before exiting.

When stopping the load generator programmatically, use:

```bash
kill -TERM "${LOAD_PID}"
wait "${LOAD_PID}" || true
```

Do not use:

```bash
kill -9
```

because `SIGKILL` cannot be handled by the script and would prevent the final summary from being generated.

# 16. Topology Spread During Node Loss

With only two worker nodes, the replacement replica may remain `Pending` while one worker is drained if strict topology spreading prevents both replicas from running on the same worker.

For example:

```text
Worker 0
SchedulingDisabled

Worker 1
└── Greeter Pod B

Pending
└── Greeter Pod C
```

This does not necessarily indicate a failure of the resilience requirement.

The primary requirement is that the service remains available after losing one node.

The surviving replica continues serving requests.

In a larger production cluster, additional worker capacity would normally allow Kubernetes to restore the desired replica count automatically.

# 22. Uncordon Does Not Rebalance Existing Pods

`kubectl uncordon` makes the worker schedulable again.

It does not automatically move healthy pods from another worker back onto the restored worker.

For example, if Kubernetes already has:

```text
Worker 0
└── empty

Worker 1
├── Pod A
└── Pod B
```

uncordoning Worker 0 does not automatically rebalance Pod A or Pod B.

Kubernetes generally leaves healthy running pods where they are.

A new scheduling event is required before a pod is placed on the restored worker.

This distinction is important:

```text
uncordon
   │
   ▼
allow future scheduling

not

uncordon
   │
   ▼
rebalance all pods
```

# 26. Rolling Update Test

The second resilience test validates application availability during a Deployment rollout.

The expected lifecycle is:

```text
Old Replica A
Old Replica B
      │
      ▼
New Replica C starts
      │
      ▼
/healthz = 200
/readyz  = 503
      │
      │ warm-up
      ▼
/readyz = 200
      │
      ▼
New Replica C receives traffic
      │
      ▼
Old Replica A receives SIGTERM
      │
      ▼
Old Replica A immediately becomes unready
      │
      ▼
Existing requests drain
      │
      ▼
Old Replica A exits
```

The same process repeats for the second replica.

---

# 27. Why the Rolling Update Test Matters

The application intentionally has non-trivial lifecycle behavior.

During startup:

```text
/healthz → 200
/readyz  → 503
```

until the warm-up period finishes.

During shutdown:

```text
SIGTERM
   │
   ▼
/readyz → 503 immediately
   │
   ▼
shutdown delay
   │
   ▼
in-flight request drain
   │
   ▼
process exits
```

The exercise explicitly describes this behavior so that the Kubernetes configuration can be tested against it. :contentReference[oaicite:0]{index=0}

# 37. Expected In-Flight Behavior

The expected sequence is:

```text
/work?ms=15000
      │
      ▼
Request accepted by Pod A
      │
      ▼
Pod A receives SIGTERM
      │
      ▼
Pod A becomes unready
      │
      ├── New requests go elsewhere
      │
      └── Existing request continues
                  │
                  ▼
             HTTP 200
```

This demonstrates that readiness and graceful shutdown have different responsibilities:

```text
Readiness
   │
   └── controls whether NEW traffic should arrive

Graceful shutdown
   │
   └── allows EXISTING traffic to complete
```

This is a stronger resilience demonstration than simply showing that the Deployment eventually reaches `Ready`.

# 38. Node Drain Success Criteria

The worker-drain test is successful when:

```text
✓ Two production replicas are initially available
✓ Replicas are distributed across worker nodes
✓ Continuous traffic is started before disruption
✓ One worker is drained
✓ The pod on that worker is evicted
✓ Another replica remains available
✓ Requests continue through Envoy Gateway
✓ Worker is successfully uncordoned
✓ Worker returns to Ready state
✓ Request results are captured
```

The ideal client result is:

```text
Failed requests: 0
```

---

# 39. Rolling Update Success Criteria

The rolling-update test is successful when:

```text
✓ Continuous traffic is active before rollout
✓ New pod initially remains unready during warm-up
✓ Existing ready replicas continue serving
✓ New pod becomes ready before receiving normal traffic
✓ Old pod becomes unready during shutdown
✓ Rollout completes successfully
✓ Request results are captured
```

The ideal client result is:

```text
Failed requests: 0
```

# 42. Design Decisions

## Test Through Envoy Gateway

Traffic is sent through:

```text
localhost:8080
```

with:

```text
Host: prod.greeter.local
```

rather than directly to a pod or Service.

This tests the complete production request path.

---

## Record Every Request

Each request is stored with:

```text
timestamp
HTTP status
latency
result
```

This provides better evidence than only checking whether the Deployment eventually became healthy.

---

## Summarize on Exit

The load generator calculates the final result when it receives a termination signal.

This allows the same utility to be reused by both:

```text
node-drain-test.sh
rolling-update-test.sh
```

without duplicating statistics logic.

---

## Restore the Node Explicitly

`kubectl drain` leaves the node cordoned.

Therefore the test explicitly executes:

```bash
kubectl uncordon
```

and waits for:

```text
Ready
```

before completing.

This prevents the resilience test from leaving the development cluster in a degraded scheduling state.

---

## Do Not Expect Automatic Rebalancing

Uncordoning a worker allows future scheduling but does not automatically redistribute healthy running pods.

This is expected Kubernetes behavior and is not treated as a failure of the test.

---

## Use the Real Deployment Path

Rolling updates are triggered through the existing:

```text
Terraform → Helm → Kubernetes
```

deployment path rather than directly patching the Deployment.

This makes the resilience test representative of how application changes are actually deployed.
