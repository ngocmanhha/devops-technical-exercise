# Step 4 — Deploy Dev and Prod Environments with Terraform

## Objective

Use Terraform to deploy the packaged Greeter Helm chart into two separate environments:

- `dev`
- `prod`

Both environments use the same reusable Terraform configuration and the same Helm package while allowing environment-specific configuration.

The environments differ at least in:

```text
GREETING_NAME
replicaCount
```

They also use separate Kubernetes namespaces and Gateway API hostnames so each environment can be accessed independently.

---

# 1. Deployment Architecture

Terraform manages two independent Greeter Helm releases:

```text
                         Terraform
                             │
                             ▼
                    Shared Configuration
                             │
                  ┌──────────┴──────────┐
                  │                     │
                  ▼                     ▼
                 dev                   prod
                  │                     │
                  ▼                     ▼
             greeter-dev          greeter-prod
              namespace             namespace
                  │                     │
                  ▼                     ▼
             Helm Release          Helm Release
                  │                     │
                  ▼                     ▼
           Greeter Service       Greeter Service
                  │                     │
                  ▼                     ▼
             HTTPRoute             HTTPRoute
                  │                     │
                  └──────────┬──────────┘
                             │
                             ▼
                   what3words-gateway
                             │
                             ▼
                        Envoy Proxy
                             │
                             ▼
                      k3d Load Balancer
                             │
                             ▼
                       localhost:8080
```

The same application package is used for both environments.

Environment differences are supplied as deployment configuration rather than maintaining separate copies of the infrastructure definition.

---

# 2. Environment Configuration

The two environments have different runtime characteristics.

Example:

| Setting | Dev | Prod |
|---|---|---|
| Namespace | `greeter-dev` | `greeter-prod` |
| Greeting | `what3words Dev` | `what3words Production` |
| Replicas | `1` | `2` |
| Version | `dev` | `prod` |
| Hostname | `dev.greeter.local` | `prod.greeter.local` |

The important requirement is:

```text
                   DEV                         PROD

GREETING_NAME      what3words Dev              what3words Production

replicaCount       1                           2
```

The environments can additionally use different CPU and memory requests/limits.

---

# 3. Reusable Environment Model

The Terraform configuration is designed so that `dev` and `prod` are instances of the same deployment model.

Conceptually:

```text
                    Greeter Deployment
                           │
                 reusable definition
                           │
                 ┌─────────┴─────────┐
                 │                   │
                 ▼                   ▼
                dev                 prod
                 │                   │
          environment values   environment values
```

This avoids maintaining separate copies such as:

```text
terraform/dev/
terraform/prod/
```

with duplicated resources.

Instead, environment-specific values are supplied to the same reusable deployment logic.

This makes adding another environment straightforward:

```text
dev
prod
staging
```

without duplicating the overall infrastructure configuration.

---

# 4. Kubernetes Namespaces

Each environment is deployed into its own Kubernetes namespace.

Dev:

```text
greeter-dev
```

Prod:

```text
greeter-prod
```

This provides basic isolation between the two application environments.

The resulting cluster layout is:

```text
what3words-exercise
│
├── envoy-gateway-system
│   │
│   ├── Envoy Gateway
│   ├── Envoy Proxy
│   └── what3words-gateway
│
├── greeter-dev
│   │
│   ├── Deployment
│   ├── Service
│   ├── HTTPRoute
│   └── PDB
│
└── greeter-prod
    │
    ├── Deployment
    ├── Service
    ├── HTTPRoute
    └── PDB
```

The Envoy Gateway infrastructure remains shared.

The Greeter application resources remain environment-specific.

# 5. Helm Package

Terraform deploys the Helm package created and signed in Step 3.

The deployment artifact is:

```text
dist/
├── greeter-0.1.0.tgz
└── greeter-0.1.0.tgz.prov
```

Both environments use:

```text
greeter-0.1.0.tgz
```

This means the deployment process follows:

```text
Application Source
       │
       ▼
Docker Image
       │
       ▼
Helm Chart
       │
       ▼
Package + Sign
       │
       ▼
greeter-0.1.0.tgz
       │
       ▼
Terraform
       │
   ┌───┴───┐
   ▼       ▼
  dev     prod
```

Terraform does not rebuild the application or regenerate the Helm chart.

It consumes the previously created deployment artifact.

# 6. Verify the Helm Package Before Deployment

Before running Terraform, verify the signed Helm package:

```bash
helm verify \
  dist/greeter-0.1.0.tgz \
  --keyring .helm-signing/pubring.gpg
```

The verification should succeed before deployment continues.

This validates:

```text
Package integrity     ✓
GPG signature         ✓
Expected signer       ✓
```

The intended workflow is:

```text
Helm Package
     │
     ▼
helm verify
     │
     ├── Failed ──────► Stop deployment
     │
     └── Success
           │
           ▼
       Terraform
```

This keeps package verification separate from infrastructure deployment.

# 9. Gateway Hostnames

Because both environments use the same shared Gateway, their HTTPRoutes must be distinguishable.

The Helm chart supports Gateway hostnames through:

```text
gateway.hostnames
```

The value is a list rather than a single hostname.

Conceptually:

```yaml
gateway:
  hostnames:
    - dev.greeter.local
```

and:

```yaml
gateway:
  hostnames:
    - prod.greeter.local
```

This allows the Helm chart to support one or multiple hostnames for an environment.

For example:

```yaml
gateway:
  hostnames:
    - prod.greeter.local
    - greeter.local
```

The HTTPRoute uses the configured hostnames when matching requests.

---

# 10. Why Hostnames Are Required

Without environment-specific hostnames, both HTTPRoutes could match:

```text
/
```

on the same Gateway.

That would make routing ambiguous.

Instead:

```text
dev.greeter.local
        │
        ▼
greeter-dev HTTPRoute
        │
        ▼
greeter-dev Service
```

and:

```text
prod.greeter.local
        │
        ▼
greeter-prod HTTPRoute
        │
        ▼
greeter-prod Service
```

Both routes still attach to:

```text
what3words-gateway
```

but requests are routed according to the HTTP `Host` header.

---

# 11. Final Gateway Architecture

The resulting Gateway API architecture is:

```text
                         localhost:8080
                               │
                               ▼
                        k3d Load Balancer
                               │
                               ▼
                           Envoy Proxy
                               │
                               ▼
                    what3words-gateway
                               │
                ┌──────────────┴──────────────┐
                │                             │
          Host header:                  Host header:
      dev.greeter.local             prod.greeter.local
                │                             │
                ▼                             ▼
        Dev HTTPRoute                 Prod HTTPRoute
                │                             │
                ▼                             ▼
        Dev Greeter Service           Prod Greeter Service
                │                             │
                ▼                       ┌─────┴─────┐
          Dev Replica                  ▼           ▼
                                    Prod 1      Prod 2
```

This allows both environments to share the same external entry point.

# 33. Optional Local DNS Entries

Instead of manually specifying the `Host` header for every request, local DNS entries can be added.

For local testing:

```text
127.0.0.1 dev.greeter.local
127.0.0.1 prod.greeter.local
```

After configuring local name resolution, requests can be simplified to:

```bash
curl http://dev.greeter.local:8080/
```

and:

```bash
curl http://prod.greeter.local:8080/
```

This is optional.

Using the explicit `Host` header remains sufficient for validating Gateway API routing.

# 36. Update an Environment

Environment configuration can be changed and then applied through Terraform.

The workflow is:

```text
Change environment configuration
             │
             ▼
      terraform fmt
             │
             ▼
     terraform validate
             │
             ▼
       terraform plan
             │
             ▼
       review changes
             │
             ▼
       terraform apply
```

For example, changing only the dev greeting should result in Terraform planning a change only to the dev Helm release.

The production deployment should remain unchanged.

This demonstrates that the two environments are independently managed despite sharing the same infrastructure definition.

# 38. Destroy the Terraform Environments

To remove the Terraform-managed application environments:

```bash
terraform destroy
```

Review the plan carefully before confirming.

This removes:

```text
greeter-dev Helm release
greeter-prod Helm release
```

and resources managed through those releases.

The shared platform infrastructure such as Envoy Gateway should remain if it is not part of this Terraform configuration.

This separation is intentional:

```text
Platform Lifecycle
       │
       ├── Envoy Gateway
       └── Shared Gateway

Application Lifecycle
       │
       ├── greeter-dev
       └── greeter-prod
```

# 39. Troubleshooting

## Terraform Cannot Connect to Kubernetes

Verify the cluster:

```bash
kubectl \
  --context k3d-what3words-exercise \
  get nodes
```

Check available contexts:

```bash
kubectl config get-contexts
```

Ensure:

```text
k3d-what3words-exercise
```

exists.

---

## Helm Release Fails During Apply

Check releases:

```bash
helm list \
  --all-namespaces
```

Inspect the environment:

```bash
kubectl get events \
  -n greeter-dev \
  --sort-by=.lastTimestamp
```

or:

```bash
kubectl get events \
  -n greeter-prod \
  --sort-by=.lastTimestamp
```

Check pods:

```bash
kubectl get pods \
  -n greeter-dev
```

```bash
kubectl get pods \
  -n greeter-prod
```

---

## Pods Stay NotReady

Check:

```bash
kubectl describe pod \
  -n greeter-dev \
  <pod-name>
```

Remember that the application intentionally returns:

```text
/readyz = 503
```

during its configured warm-up period.

Therefore a pod being temporarily:

```text
Running
0/1 Ready
```

during startup is expected.

---

```bash
kubectl describe httproute \
  -n greeter-dev
```

```bash
kubectl describe httproute \
  -n greeter-prod
```


```text

```



# 40. Design Decisions

## One Reusable Terraform Configuration

Dev and prod are modeled as different instances of the same deployment configuration.

This avoids duplicating infrastructure definitions and ensures both environments follow the same deployment pattern.

Environment-specific differences remain data rather than duplicated infrastructure code.

---

## Separate Namespaces

Each environment receives its own Kubernetes namespace:

```text
greeter-dev
greeter-prod
```

This provides a clear operational boundary while allowing both environments to share cluster-level infrastructure.

---

## Same Helm Artifact

Both environments deploy the same packaged Helm artifact:

```text
greeter-0.1.0.tgz
```

The package itself does not contain environment-specific configuration.

Instead:

```text
Same package
     +
Different deployment values
     =
Different environments
```

This is preferable to producing:

```text
greeter-dev.tgz
greeter-prod.tgz
```

because the application artifact should remain environment independent.

---

## Signed Artifact Verification

The Helm package is verified before Terraform deployment.

Signing and verification remain separate from Terraform because they belong to the artifact build and release lifecycle.

Terraform consumes an already-created deployment artifact.

---

## Environment-Specific Runtime Configuration

Values such as:

```text
GREETING_NAME
replicaCount
VERSION
resources
gateway.hostnames
```

can vary between environments.

The container image remains unchanged.

---

## Shared Envoy Gateway

Envoy Gateway and `what3words-gateway` are treated as shared platform infrastructure.

Terraform's application deployment attaches environment-specific HTTPRoutes to that shared Gateway.

This keeps the ownership model clear:

```text
Platform
└── Gateway

Application Environment
└── HTTPRoute
```

---

## Hostname-Based Routing

Environment-specific hostnames are used rather than exposing both applications with identical `/` routes.

The Helm chart accepts:

```text
gateway.hostnames
```

as a list.

This provides flexibility for an environment to expose one or multiple DNS names.

For this exercise:

```text
dev.greeter.local
prod.greeter.local
```

are sufficient.

---

## Production Replica Count

Production uses more replicas than development:

```text
dev  = 1
prod = 2
```

This demonstrates environment-specific scaling while avoiding duplicated deployment configuration.

Production also benefits from the topology spread configuration introduced in Step 3.

---

## Terraform Owns Deployment, Not Packaging

Responsibilities are intentionally separated:

```text
Docker
   │
   └── Build application image

Helm
   │
   ├── Package Kubernetes application
   └── Sign deployment artifact

Terraform
   │
   └── Deploy environment instances

Envoy Gateway
   │
   └── Route external traffic
```

Terraform therefore does not build the Docker image or package/sign the Helm chart.
