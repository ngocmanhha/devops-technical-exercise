# Extension B — Observability with Prometheus Operator

## Objective

Add Kubernetes-native observability for the Greeter application using **Prometheus Operator** and `kube-prometheus-stack`.

The implementation provides:

- Prometheus Operator
- Prometheus
- `ServiceMonitor` resources for application metric discovery
- `PrometheusRule` resources for alerting
- Dynamic alert rule definitions from Helm `values.yaml`
- Separate monitoring for dev and prod
- A production-focused 5xx error-rate alert
- Reproducible alert testing using `/boom`
- Evidence capture for both rule loading and alert firing

The application already exposes Prometheus-compatible metrics through:

```text
GET /metrics
```

including request counters, latency histograms, build information, and readiness metrics. :contentReference[oaicite:0]{index=0}

---

# 1. Architecture

The monitoring architecture is:

```text
                    Greeter Application
                            │
                            │ /metrics
                            ▼
                     Greeter Service
                            │
                            ▼
                       ServiceMonitor
                            │
                            ▼
                  Prometheus Operator
                            │
                            ▼
                        Prometheus
                            │
                ┌───────────┴───────────┐
                │                       │
                ▼                       ▼
          Metrics Queries         PrometheusRule
                                        │
                                        ▼
                                  Alert Evaluation
                                        │
                                 ┌──────┴──────┐
                                 │             │
                                 ▼             ▼
                              Pending        Firing
```

Monitoring resources are created by the Greeter Helm chart.

Prometheus infrastructure is deployed separately in the `monitoring` namespace.

# 6. Helm Monitoring Configuration

Monitoring is configurable through:

```text
charts/greeter/values.yaml
```

Example:

```yaml
monitoring:
  enabled: true

  serviceMonitor:
    enabled: true
    interval: 15s
    scrapeTimeout: 5s

  prometheusRule:
    enabled: true

    rules:
      - alertName: GreeterHigh5xxErrorRate

        expr: |
          (
            sum(
              rate(
                greeter_http_requests_total{
                  status=~"5..",
                  path!~"/healthz|/readyz"
                }[1m]
              )
            )
            /
            sum(
              rate(
                greeter_http_requests_total{
                  path!~"/healthz|/readyz"
                }[1m]
              )
            )
          ) > 0.10
          and
          sum(
            rate(
              greeter_http_requests_total{
                path!~"/healthz|/readyz"
              }[1m]
            )
          ) > 0

        for: 2m

        labels:
          severity: critical

        annotations:
          summary: Greeter has a high HTTP 5xx error rate
          description: More than 10% of user-facing Greeter requests have returned HTTP 5xx responses for 2 minutes.
```

The monitoring block can be disabled completely:

```yaml
monitoring:
  enabled: false
```

This allows the Greeter chart to remain deployable in clusters without Prometheus Operator.

# 7. ServiceMonitor

The Helm chart creates a `ServiceMonitor` when monitoring is enabled.

The ServiceMonitor targets the Greeter Service using its standard Helm labels.

Conceptually:

```text
ServiceMonitor
      │
      │ selector
      ▼
Greeter Service
      │
      │ named port: http
      ▼
Greeter Pod
      │
      ▼
GET /metrics
```

The Service port should have a stable name:

```yaml
ports:
  - name: http
    port: 80
    targetPort: http
```

The application container should expose:

```yaml
ports:
  - name: http
    containerPort: 8080
```

The ServiceMonitor endpoint uses:

```text
port: http
path: /metrics
```

with:

```text
scrape interval  = 15s
scrape timeout   = 5s
```

---

# 8. No Custom Scrape Label Required

A custom label such as:

```text
observability.what3words.io/scrape=true
```

is not required.

That approach is useful with raw Prometheus Kubernetes service discovery, but Prometheus Operator uses the `ServiceMonitor` selector instead.

The relationship is therefore:

```text
Prometheus
    │
    ▼
ServiceMonitor
    │
    │ matchLabels
    ▼
Greeter Service
```

The ServiceMonitor reuses the same selector labels already applied to the Greeter Service.

---

# 9. Dynamic Prometheus Rules

Alert rules are not hard-coded into `prometheusrule.yaml`.

Instead, the Helm template iterates through:

```text
monitoring.prometheusRule.rules
```

This keeps the template generic.

Conceptually:

```text
values.yaml
     │
     ├── Alert 1
     ├── Alert 2
     └── Alert N
          │
          ▼
prometheusrule.yaml
          │
          ▼
PrometheusRule
```

This allows new alerts to be added without modifying the Helm template.

For example:

```yaml
rules:
  - alertName: GreeterHigh5xxErrorRate
    ...

  - alertName: GreeterNotReady
    ...

  - alertName: GreeterHighLatency
    ...
```

Only the alert configuration changes.

# 12. Alert Selection

The selected alert is:

```text
GreeterHigh5xxErrorRate
```

The alert fires when more than:

```text
10%
```

of user-facing requests return a 5xx response for:

```text
2 minutes
```

This is more meaningful than alerting on a single HTTP 500 response.

The alert expression is:

```promql
(
  sum(
    rate(
      greeter_http_requests_total{
        status=~"5..",
        path!~"/healthz|/readyz"
      }[1m]
    )
  )
  /
  sum(
    rate(
      greeter_http_requests_total{
        path!~"/healthz|/readyz"
      }[1m]
    )
  )
) > 0.10
and
sum(
  rate(
    greeter_http_requests_total{
      path!~"/healthz|/readyz"
    }[1m]
  )
) > 0
```

---

# 13. Why Health Endpoints Are Excluded

The alert explicitly excludes:

```text
/healthz
/readyz
```

using:

```promql
path!~"/healthz|/readyz"
```

This is important because `/readyz` intentionally returns HTTP `503`:

- during startup
- as soon as shutdown begins

Those responses are expected lifecycle behavior rather than application failures. :contentReference[oaicite:2]{index=2} :contentReference[oaicite:3]{index=3}

Without this exclusion, normal rolling deployments or pod shutdowns could artificially increase the observed 5xx error rate.

The alert therefore focuses on user-facing traffic.

---

# 14. Traffic Guard

The expression also includes:

```promql
sum(
  rate(
    greeter_http_requests_total{
      path!~"/healthz|/readyz"
    }[1m]
  )
) > 0
```

This ensures there is actual application traffic before evaluating the error-rate threshold.

The intended logic is:

```text
No traffic
   │
   └── Do not alert

Traffic exists
   │
   ▼
Calculate 5xx ratio
   │
   ├── <= 10% → healthy
   │
   └── > 10%
          │
          ▼
        Pending
          │
          │ 2 minutes
          ▼
        Firing
```

---

# 15. Alert Duration

The alert uses:

```yaml
for: 2m
```

This prevents short spikes from immediately triggering the alert.

Alert lifecycle:

```text
Expression false
      │
      ▼
   Inactive
      │
      │ error ratio > 10%
      ▼
    Pending
      │
      │ remains > 10% for 2m
      ▼
    Firing
```

If the error rate drops below the threshold before two minutes, the alert returns to the inactive state.

# 33. Design Decisions

## Prometheus Operator Instead of Raw Prometheus

Prometheus Operator was selected because it provides Kubernetes-native monitoring abstractions:

```text
ServiceMonitor
PrometheusRule
```

rather than requiring manually maintained Prometheus scrape configuration.

This keeps monitoring configuration close to the application resources it describes.

---

## ServiceMonitor Instead of Custom Scrape Labels

The implementation uses:

```text
ServiceMonitor
```

to discover Greeter targets.

A custom scrape annotation or custom label is unnecessary because target selection is already represented declaratively through the ServiceMonitor.

---

## Dynamic Rules from values.yaml

Alert rules are defined in:

```text
values.yaml
```

rather than hard-coded into the Helm template.

This provides:

```text
Generic template
+
Environment/configuration data
```

and allows new rules to be added without changing the template structure.

---

## One Meaningful Alert

Only one alert is implemented:

```text
GreeterHigh5xxErrorRate
```

This is deliberate.

The exercise asks for one alert worth waking someone up for rather than a large collection of low-value alerts. :contentReference[oaicite:5]{index=5}

---

## Error Ratio Instead of Single Failure

A single HTTP 500 is not considered page-worthy.

The alert requires:

```text
> 10% HTTP 5xx
for 2 minutes
```

which filters short-lived or isolated failures.

---

## Health Paths Excluded

`/healthz` and `/readyz` are excluded because their behavior reflects application lifecycle and Kubernetes health checking rather than user requests.

In particular, `/readyz` intentionally returns `503` during startup and shutdown. :contentReference[oaicite:6]{index=6}

---

## Prod-Focused Alert Testing

The `/boom` test is performed against:

```text
prod.greeter.local
```

because production-facing service failures are the scenario in which this alert would be operationally meaningful.

Development failures should not normally result in paging.

---

## Evidence Through Prometheus API

Evidence is captured using:

```text
/api/v1/rules
/api/v1/alerts
/api/v1/targets
```

rather than relying only on screenshots.

This makes the evidence:

```text
machine-readable
reproducible
easy to review
```
