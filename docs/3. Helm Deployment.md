# Step 3 — Package and Deploy the Application with Helm

## Objective

Package the Go application as a **hand-written Helm chart** and deploy it to the local `what3words-exercise` Kubernetes cluster.

The deployment provides:

- Configurable runtime settings
- Multiple application replicas
- Correct Kubernetes liveness and readiness probes
- Graceful termination
- Rolling updates
- Replica distribution across worker nodes
- Pod disruption protection
- External access through Kubernetes Gateway API
- Envoy Gateway `v1.9.0`
- End-to-end Gateway API validation
- Signed Helm packages with provenance verification

The Helm chart is located at:

```text
charts/greeter
```

The chart is intentionally small and hand-written rather than generated from the default `helm create` scaffold.

---

# 1. Architecture

The deployment architecture is:

```text
                        Local Machine
                             │
                      localhost:8080
                             │
                             ▼
                    k3d Load Balancer
                             │
                             ▼
                        Envoy Proxy
                             │
                             ▼
                   what3words-gateway
                       (Gateway)
                             │
                             ▼
                    Greeter HTTPRoute
                             │
                             ▼
                     Greeter Service
                             │
                  ┌──────────┴──────────┐
                  │                     │
                  ▼                     ▼
           Greeter Replica 1     Greeter Replica 2
                  │                     │
                  ▼                     ▼
                Agent 0               Agent 1
```

The responsibilities are separated between the platform and application layers:

```text
Platform Infrastructure
│
├── Envoy Gateway v1.9.0
├── GatewayClass
└── Gateway
       │
       ▼
Application Helm Chart
│
├── Deployment
├── Service
├── HTTPRoute
└── PodDisruptionBudget
```

```yaml

  drainTimeoutSeconds: 20

  type: ClusterIP
  port: 80

  enabled: true

  name: what3words-gateway
  namespace: envoy-gateway-system

  requests:
    cpu: 50m
    memory: 32Mi

  limits:
    cpu: 250m
    memory: 128Mi

probes:
  liveness:
    initialDelaySeconds: 5
    periodSeconds: 10
    timeoutSeconds: 2
    failureThreshold: 3

  readiness:
    periodSeconds: 5
    timeoutSeconds: 2
    failureThreshold: 2

podDisruptionBudget:
  enabled: true
  minAvailable: 1

  enabled: true
  maxSkew: 1
  topologyKey: kubernetes.io/hostname

tolerations: []
```

Application configuration remains outside the container image so the same immutable image can be reused across environments.

# 5. Runtime Configuration

The Helm deployment provides the following environment variables to the Go application:

```text
GREETING_NAME
PORT
VERSION
WARMUP_SECONDS
SHUTDOWN_DELAY_SECONDS
DRAIN_TIMEOUT_SECONDS
```

`GREETING_NAME` is required by the application.

The template therefore validates it:

```yaml
- name: GREETING_NAME
  value: {{ required "application.greetingName is required" .Values.application.greetingName | quote }}
```

A missing greeting therefore causes Helm rendering to fail rather than allowing Kubernetes to deploy a container that immediately exits.

# 6. Liveness Probe

The liveness probe uses:

```text
GET /healthz
```

Example:

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: http

  initialDelaySeconds: {{ .Values.probes.liveness.initialDelaySeconds }}
  periodSeconds: {{ .Values.probes.liveness.periodSeconds }}
  timeoutSeconds: {{ .Values.probes.liveness.timeoutSeconds }}
  failureThreshold: {{ .Values.probes.liveness.failureThreshold }}
```

The application returns HTTP `200` from `/healthz` while the process is alive, including while the application is warming up.

Therefore `/healthz` is the correct endpoint for determining whether Kubernetes should restart the process.

---

# 7. Readiness Probe

The readiness probe uses:

```text
GET /readyz
```

Example:

```yaml
readinessProbe:
  httpGet:
    path: /readyz
    port: http

  periodSeconds: {{ .Values.probes.readiness.periodSeconds }}
  timeoutSeconds: {{ .Values.probes.readiness.timeoutSeconds }}
  failureThreshold: {{ .Values.probes.readiness.failureThreshold }}
```

The startup lifecycle is:

```text
Application starts
        │
        ▼
HTTP listener starts
        │
        ├── /healthz = 200
        │
        └── /readyz  = 503
                 │
                 │ WARMUP_SECONDS
                 │
                 ▼
             /readyz = 200
```

The default warm-up period is:

```text
30 seconds
```

Using `/readyz` for liveness would therefore be incorrect because Kubernetes could restart a healthy application simply because it has not completed its warm-up period.

---

# 8. Graceful Shutdown

The application implements its own graceful shutdown lifecycle.

When Kubernetes sends `SIGTERM`:

```text
SIGTERM
   │
   ▼
/readyz = 503
   │
   ▼
Application remains alive
   │
   │ SHUTDOWN_DELAY_SECONDS
   ▼
Stops accepting new connections
   │
   │ DRAIN_TIMEOUT_SECONDS
   ▼
Waits for in-flight requests
   │
   ▼
Exit 0
```

The default values are:

```text
Shutdown delay = 10 seconds
Drain timeout  = 20 seconds
```

The pod therefore uses:

```yaml
terminationGracePeriodSeconds: 40
```

This provides:

```text
10 seconds shutdown delay
+
20 seconds drain timeout
+
10 seconds safety margin
=
40 seconds
```

A Kubernetes `preStop` sleep is intentionally not used.

The application already performs its own shutdown delay, so an additional sleep would duplicate the lifecycle logic and delay delivery of `SIGTERM`.

---

# 9. Rolling Updates

The Deployment uses:

```yaml
strategy:
  type: RollingUpdate

  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

This is particularly important because new pods remain unready during the warm-up period.

During an update:

```text
Existing deployment

Agent 0                       Agent 1
   │                             │
   ▼                             ▼
Pod v1 READY                 Pod v1 READY


New pod starts

Agent 0                       Agent 1
   │                             │
   ├── Pod v1 READY              └── Pod v1 READY
   │
   └── Pod v2 NOT READY
           │
           │ 30 second warm-up
           ▼
       Pod v2 READY
```

`maxUnavailable: 0` prevents Kubernetes from intentionally reducing the number of available replicas during the rolling update.

---

# 10. Worker-Only Scheduling

Application pods should not run on the Kubernetes control-plane node.

This is configured through Helm values:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: node-role.kubernetes.io/control-plane
              operator: DoesNotExist
```

The Deployment renders the configuration generically:

```yaml
{{- with .Values.affinity }}
affinity:
  {{- toYaml . | nindent 8 }}
{{- end }}
```

The resulting Kubernetes structure must be:

```yaml
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: node-role.kubernetes.io/control-plane
                    operator: DoesNotExist
```

The deprecated label:

```text
node-role.kubernetes.io/master
```

is intentionally not used.

The current label is:

```text
node-role.kubernetes.io/control-plane
```

# 11. Replica Distribution

Two replicas alone do not guarantee node-level availability.

Both pods could otherwise be scheduled onto the same worker.

The chart therefore uses topology spread constraints:

```yaml
topologySpreadConstraints:
  - maxSkew: 1

    topologyKey: kubernetes.io/hostname

    whenUnsatisfiable: DoNotSchedule

    labelSelector:
      matchLabels:
        app.kubernetes.io/name: greeter
```

The expected placement is:

```text
Agent 0                       Agent 1
   │                             │
   ▼                             ▼
Greeter Pod 1                Greeter Pod 2
```

rather than:

```text
Agent 0                       Agent 1
   │                             │
   ├── Greeter Pod 1             └── empty
   │
   └── Greeter Pod 2
```

Verify:

```bash
kubectl get pods \
  -n greeter \
  -o wide
```

The two replicas should normally run on:

```text
k3d-what3words-exercise-agent-0
k3d-what3words-exercise-agent-1
```

---

# 12. Pod Disruption Budget

The application creates a PodDisruptionBudget:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget

spec:
  minAvailable: 1
```

With the default deployment:

```text
replicas     = 2
minAvailable = 1
```

This prevents voluntary Kubernetes operations such as a node drain from intentionally disrupting both application replicas simultaneously.

The PDB complements topology spreading.

It does not protect against an unexpected node failure, so replica distribution remains necessary.

# 14. Gateway API and Envoy Gateway

The cluster uses:

```text
Envoy Gateway v1.9.0
```

as the Gateway API implementation.

The networking responsibilities are separated into:

```text
Platform Layer
│
├── Envoy Gateway
├── GatewayClass
└── Gateway

│
```

This keeps shared traffic infrastructure independent from application-specific routing.

# 18. HTTPRoute

The application Helm chart owns the `HTTPRoute`.

Example:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute

metadata:
  name: {{ include "greeter.fullname" . }}

spec:
  parentRefs:
    - name: {{ .Values.gateway.name }}
      namespace: {{ .Values.gateway.namespace }}

  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /

      backendRefs:
        - name: {{ include "greeter.fullname" . }}
          port: {{ .Values.service.port }}
```

The resulting routing path is:

```text
Gateway
   │
   ▼
HTTPRoute
   │
   ▼
Service
   │
   ▼
Ready Greeter Pods
```

# 26. Validate HTTPRoute

Check:

```bash
kubectl get httproute \
  -n greeter
```

```bash
kubectl describe httproute \
  -n greeter
```

Print route conditions:

```bash
kubectl get httproute \
  -n greeter \
  -o jsonpath='{range .items[*].status.parents[*].conditions[*]}{.type}={.status}{" reason="}{.reason}{"\n"}{end}'
```

The important conditions are:

```text

```

`ResolvedRefs=True` indicates that references such as the backend Service were successfully resolved.

If `ResolvedRefs=False`, inspect the reason carefully.

```text
BackendNotFound
RefNotPermitted
```

# 33. Envoy Troubleshooting Matrix

Use the following sequence to isolate networking failures.

| Test | Result | Likely Problem |
|---|---|---|
| Service port-forward fails | Failure | Application, pod, readiness, or Service |
| Service works, Envoy port-forward fails | Failure | Gateway, HTTPRoute, or Envoy |
| Envoy port-forward works | Success | Envoy routing is functioning |
| Envoy works, `localhost:8080` fails | Failure | k3d load-balancer/host-port mapping |
| HTTPRoute `Accepted=False` | Failure | Gateway/route attachment |
| HTTPRoute `ResolvedRefs=False` | Failure | Backend reference |
| Gateway `Programmed=False` | Failure | Envoy/Gateway provisioning |
| Service has no endpoints | Failure | Service selector or pod readiness |

A particularly useful distinction is:

```text
localhost:18080 works
localhost:8888 fails
```

This indicates:

```text
Application  ✓
Service      ✓
Envoy path   ✗
```

Whereas:

```text
localhost:8888 works
localhost:8080 fails
```

indicates:

```text
Application       ✓
Service           ✓
HTTPRoute         ✓
Gateway           ✓
Envoy Proxy       ✓
k3d external path ✗
```

This greatly reduces troubleshooting time.

# 34. Envoy Gateway Acceptance Criteria

Envoy Gateway can be considered operational when:

```text
Envoy Gateway controller       Running
GatewayClass                   Accepted
Gateway                        Accepted=True
Gateway                        Programmed=True
HTTPRoute                      Accepted=True
HTTPRoute                      ResolvedRefs=True
Greeter Service               Has endpoints
Direct Service test           HTTP 200
Direct Envoy test             HTTP 200
localhost:8080 test           HTTP 200
```

The strongest functional proof is:

```bash
curl -v http://localhost:8888/
```

through the port-forwarded Envoy data-plane Service.

If that request reaches Greeter successfully, Envoy has correctly processed:

```text
Gateway
   +
HTTPRoute
   +
Backend Service
```

# 38. Helm Chart Signing

The Helm chart is cryptographically signed using GPG.

Packaging produces:

```text
greeter-0.1.0.tgz
greeter-0.1.0.tgz.prov
```

The provenance file allows the package to be independently verified before installation.

Signing provides assurance that:

- The chart was signed by the expected identity
- The chart has not been modified after signing
- The artifact being installed matches the signed artifact

The private signing key must never be committed.

---

# 39. Create the Signing Key

Create a signing-only RSA4096 key:

```bash
gpg \
  --batch \
  --pinentry-mode loopback \
  --passphrase 'YOUR_PASSPHRASE' \
  --quick-generate-key \
  'what3words Helm Signing (DevOps Technical Exercise) <your.email@example.com>' \
  rsa4096 \
  sign \
  0
```

The key properties are:

```text
Real name:   what3words Helm Signing
Comment:     DevOps Technical Exercise
Email:       your.email@example.com
Algorithm:   RSA 4096
Usage:       Signing
Expiration:  Never
```

Verify:

```bash
gpg \
  --list-secret-keys \
  --keyid-format LONG
```

Avoid placing the actual production/signing passphrase directly in shell history.

---

# 40. Prepare Helm Signing Keyrings

Create:

```bash
mkdir -p .helm-signing
```

Export the secret key:

```bash
gpg \
  --export-secret-keys \
  > .helm-signing/secring.gpg
```

Export the public key:

```bash
gpg \
  --export \
  > .helm-signing/pubring.gpg
```

Add to `.gitignore`:

```gitignore
.helm-signing/
```

Never commit:

```text
.helm-signing/secring.gpg
```

---

# 41. Export the Public Signing Key

Export the public key:

```bash
gpg \
  --armor \
  --export "what3words Helm Signing" \
  > helm-signing-public.asc
```

The public key can safely be committed to the repository.

This allows an evaluator to verify the chart independently.

# 46. Design Decisions

## Helm Instead of Kustomize

Helm was selected because application configuration must vary between environments.

Values such as:

```text
replicaCount
application.greetingName
application.version
resources
```

can be changed without duplicating Kubernetes manifests.

This also integrates naturally with Terraform's Helm provider in the next step.

---

## Hand-Written Chart

The chart was written manually instead of relying on the default output of:

```bash
helm create
```

Only Kubernetes resources required by the application are included.

This keeps the package small and makes each configuration choice explainable.

---

## Gateway API Instead of Ingress

Gateway API provides a cleaner separation between platform and application networking responsibilities:

```text
Platform Team
├── GatewayClass
└── Gateway

Application
└── HTTPRoute
```

This is preferable to embedding infrastructure-specific Ingress annotations into the application chart.

---

## Envoy Gateway v1.9.0

Envoy Gateway `v1.9.0` is pinned rather than using an unversioned or `latest` installation.

This improves reproducibility and prevents changes in future Envoy Gateway releases from unexpectedly altering the exercise environment.

---

## ClusterIP Service

The application Service remains internal:

```text
ClusterIP
```

External HTTP access is managed through Gateway API rather than exposing the application directly through NodePort.

---

## Two Replicas

The default deployment uses:

```yaml
replicaCount: 2
```

This is the minimum practical replica count for demonstrating availability when one worker becomes unavailable.

---

## Topology Spread Constraints

Replica distribution uses:

```text
kubernetes.io/hostname
```

with:

```text
maxSkew = 1
```

This prevents both replicas from being intentionally concentrated on one worker when both workers are available.

---

## Node Affinity Through Values

Affinity is defined in `values.yaml` rather than hard-coded into the Deployment.

This makes scheduling policy configurable for different Kubernetes environments.

The current implementation excludes nodes with:

```text
node-role.kubernetes.io/control-plane
```

and does not use the deprecated:

```text
node-role.kubernetes.io/master
```

label.

---

## PodDisruptionBudget

The application uses:

```text
minAvailable = 1
```

to protect availability during voluntary disruptions.

The PDB complements topology spreading rather than replacing it.

---

## No preStop Sleep

No artificial `preStop` sleep is configured.

The application itself already:

1. Becomes unready after SIGTERM
2. Waits for the configured shutdown delay
3. Stops accepting connections
4. Drains in-flight requests

Duplicating the delay at the Kubernetes level would unnecessarily increase shutdown time.

---

## Local Image Import

For the local exercise:

```bash
k3d image import \
  greeter:local \
  --cluster what3words-exercise
```

is used instead of an external container registry.

A production implementation would normally use immutable image tags or digests from a secured container registry.

---

## Signed Helm Package

The Helm chart is distributed with a GPG provenance signature.

The private signing key remains outside Git.

The public key can be committed so reviewers can independently verify the package.

In a production environment, signing would normally happen through a secured CI/CD workflow rather than a developer workstation.
