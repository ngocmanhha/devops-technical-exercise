# Extension A — Continuous Integration

## Objective

Implement a GitHub Actions CI pipeline for the Greeter project.

The pipeline validates the application and infrastructure code on every relevant push or pull request without deploying infrastructure or requiring access to the local k3d cluster.

The CI pipeline covers:

- Go unit tests
- Go test coverage
- Mock Sonar code-quality analysis
- Docker image build
- Helm chart validation
- Dev and prod manifest rendering
- Gateway API resource validation
- Monitoring resource validation
- Terraform formatting and validation
- Shell script static analysis
- Final CI status aggregation

The exercise asks for a GitHub Actions workflow that runs appropriate checks for the service on push. :contentReference[oaicite:0]{index=0}

---

# 1. CI Architecture

The pipeline is designed so independent validation jobs can run in parallel.

```text
                         Push / Pull Request
                                 │
          ┌──────────────────────┼──────────────────────┐
          │                      │                      │
          ▼                      ▼                      ▼
      Go Tests              Helm Validation      Terraform Validation
          │                      │
          │                      ├── Helm lint
          │                      ├── Dev render
          │                      ├── Prod render
          │                      ├── HTTPRoute
          │                      ├── ServiceMonitor
          │                      └── PrometheusRule
          │
          ├─────────────┐
          │             │
          ▼             ▼
   Docker Build    Mock Sonar Scan

                    ShellCheck
                        │
                        ▼

               All required jobs
                        │
                        ▼
                    CI Success
```

This structure keeps CI relatively fast while making failures easy to identify.

# 2. Workflow Location

The GitHub Actions workflow is stored at:

```text
└── workflows/
    └── ci.yaml
```

The workflow contains the following jobs:

```text
test

docker
helm
terraform

ci-success
```

---

# 3. Workflow Triggers

CI runs on pushes to:

```text
main
solution
```

and pull requests targeting:

```text
main
```

Configuration:

```yaml
on:
  push:
    branches:
      - main
      - solution

  pull_request:
    branches:
      - main
```

This ensures that changes are validated both during development and before they are merged into the main branch.

---

# 4. GitHub Actions Permissions

The workflow only requires repository read access:

```yaml
permissions:
  contents: read
```

The CI pipeline does not:

```text
push Docker images
create GitHub releases
modify repository contents
deploy Kubernetes resources
apply Terraform
```

Therefore additional write permissions are unnecessary.

---

# 5. Go Tests

The first application validation job is:

```text
Go Tests
```

It checks out the repository and configures Go using the version declared by:

```text
app/go.mod
```

The workflow uses:

```yaml
uses: actions/setup-go@v5
```

with:

```yaml
go-version-file: app/go.mod
cache-dependency-path: app/go.sum
```

This avoids duplicating the Go version in the CI workflow.

---

# 6. Run Unit Tests

Tests are executed from:

```text
app/
```

using:

```bash
go test \
  -coverprofile=coverage.out \
  ./...
```

`CGO` is disabled:

```text
CGO_ENABLED=0
```

The test stage therefore performs both:

```text
Unit tests
+
Coverage collection
```

If any Go test fails, the job fails immediately.

---

# 7. Go Coverage

Test coverage is written to:

```text
app/coverage.out
```

The coverage report can be inspected using:

```bash
go tool cover \
  -func=coverage.out
```

Example output:

```text
github.com/example/greeter/main.go:42:       handler       100.0%
github.com/example/greeter/main.go:71:       healthz       100.0%
total:                                                   82.5%
```

The exact percentage depends on the application's tests.

CI does not enforce a hard-coded minimum coverage threshold.

Instead, the coverage report is made available to the code-quality stage.

---

# 8. Coverage Artifact

The Go test job uploads:

```text
app/coverage.out
```

as a GitHub Actions artifact named:

```text
go-coverage
```

The flow is:

```text
Go Tests
    │
    ▼
coverage.out
    │
    ▼
GitHub Actions Artifact
    │
    ▼
Mock Sonar Scan
```

This also demonstrates how a real code-quality job could consume test output generated by an earlier job.

# 9. Mock Sonar Analysis

The CI workflow includes:

```text
Mock Sonar Scan
```

This stage intentionally represents where SonarQube or SonarCloud would normally be integrated.

It does **not** connect to an actual SonarQube or SonarCloud server.

No external Sonar credentials are required.

---

# 10. Why Sonar Is Mocked

A real Sonar integration would require external infrastructure or credentials such as:

```text
SonarQube server
or
SonarCloud project

SONAR_TOKEN
project configuration
quality gate configuration
```

Those dependencies are not required to demonstrate the CI architecture for this exercise.

Therefore the workflow explicitly identifies the stage as:

```text
Mock Sonar Scan
```

rather than presenting it as a real security or quality scan.

In a production implementation, this stage would be replaced by an actual SonarQube or SonarCloud action and its configured quality gate.

---

# 11. Mock Sonar Input

The Sonar job depends on:

```text
Go Tests
```

using:

```yaml
needs:
  - test
```

It downloads the coverage artifact:

```text
go-coverage
```

to:

```text
app/
```

The job verifies that:

```text
app/coverage.out
```

exists before continuing.

---

# 12. Mock Coverage Reporting

The stage calculates the real overall Go coverage percentage from the test artifact:

```bash
go tool cover \
  -func=app/coverage.out
```

and extracts the total value.

The result is then presented alongside mocked quality results:

```text
Project:            what3words-exercise
Code coverage:      <actual Go coverage>
Bugs:               0
Vulnerabilities:    0
Security hotspots:  0
Code smells:        0
Quality Gate:       PASSED
```

Only the coverage value comes from the actual test report.

The Sonar findings and quality-gate result are placeholders demonstrating the expected CI integration point.

They must not be interpreted as results from a real Sonar analysis.

---

# 13. Production Sonar Replacement

In a production environment, the mock stage would be replaced with:

```text
Go Tests
    │
    ▼
coverage.out
    │
    ▼
SonarQube / SonarCloud
    │
    ├── static analysis
    ├── coverage analysis
    ├── bugs
    ├── vulnerabilities
    ├── security hotspots
    ├── code smells
    └── quality gate
           │
           ▼
        Pass / Fail
```

The rest of the CI architecture would not need to change significantly.

# 14. Docker Build Validation

The Docker job verifies that the application image can be successfully built from the repository.

It depends on:

```text
Go Tests
```

so Docker validation does not continue if the application tests fail.

The job uses:

```yaml
docker/setup-buildx-action@v3
```

and:

```yaml
docker/build-push-action@v6
```

---

# 15. Docker Build

CI builds:

```text
greeter:ci
```

using:

```yaml
push: false
platforms: linux/amd64
```

The image is intentionally **not pushed** to a registry.

The purpose of this job is only to validate:

```text
Dockerfile syntax
build stages
Go compilation inside Docker
runtime image construction
```

---

# 16. CI Docker Platform

The CI build targets:

```text
linux/amd64
```

The Dockerfile itself remains portable and can also be built for ARM64 environments such as Apple Silicon.

For example, local multi-platform builds can still target:

```text
linux/amd64
linux/arm64
```

The CI job uses only `linux/amd64` to keep validation relatively fast.

---

# 17. Docker Build Cache

GitHub Actions cache is enabled:

```yaml
cache-from: type=gha
cache-to: type=gha,mode=max
```

This allows reusable Docker build layers to be restored between workflow runs.

The expected benefit is faster subsequent builds when dependencies or earlier Docker layers have not changed.

---

# 18. Helm Validation

The Helm job validates:

```text
charts/greeter
```

without installing the chart into a Kubernetes cluster.

This is important because a normal GitHub-hosted runner does not have access to the local:

```text
what3words-exercise
```

k3d cluster.

The Helm stage therefore focuses on static chart validation and rendering.

---

# 19. Helm Lint

The first Helm validation is:

```bash
helm lint charts/greeter
```

This detects common chart problems such as:

```text
invalid templates
invalid YAML generation
missing required chart metadata
incorrect Helm template usage
```

A lint failure causes the Helm CI job to fail.

---

# 20. Render Dev Environment

The development environment is rendered using:

```bash
helm template \
  greeter \
  charts/greeter \
  --namespace greeter-dev \
  --set gateway.hostnames[0]=dev.greeter.local \
  > /tmp/greeter-dev.yaml
```

This verifies that the chart can successfully generate Kubernetes manifests for the development environment.

The expected Gateway API hostname is:

```text
dev.greeter.local
```

---

# 21. Render Prod Environment

Production is rendered separately:

```bash
helm template \
  greeter \
  charts/greeter \
  --namespace greeter-prod \
  --set gateway.hostnames[0]=prod.greeter.local \
  > /tmp/greeter-prod.yaml
```

The expected hostname is:

```text
prod.greeter.local
```

Rendering environments separately helps catch problems with environment-specific Helm configuration.

---

# 22. Validate Rendered Manifests

CI verifies that both rendered files are non-empty:

```bash
test -s /tmp/greeter-dev.yaml
test -s /tmp/greeter-prod.yaml
```

The generated resource kinds are also printed:

```bash
grep '^kind:' /tmp/greeter-dev.yaml
```

and:

```bash
grep '^kind:' /tmp/greeter-prod.yaml
```

This makes the generated resource set visible directly in the CI log.

---

# 23. Gateway API Validation

The chart uses Gateway API with Envoy Gateway.

The CI pipeline verifies that both rendered environments contain:

```text
HTTPRoute
```

using:

```bash
grep -q 'kind: HTTPRoute' /tmp/greeter-dev.yaml
grep -q 'kind: HTTPRoute' /tmp/greeter-prod.yaml
```

It also validates the expected hostnames:

```bash
grep -q 'dev.greeter.local' /tmp/greeter-dev.yaml
grep -q 'prod.greeter.local' /tmp/greeter-prod.yaml
```

This catches accidental regressions such as incorrect hostname rendering.

---

# 24. Monitoring Resource Validation

The Helm chart also contains the observability implementation from Extension B.

CI verifies that production rendering contains:

```text
ServiceMonitor
PrometheusRule
```

using:

```bash
grep -q 'kind: ServiceMonitor' /tmp/greeter-prod.yaml
grep -q 'kind: PrometheusRule' /tmp/greeter-prod.yaml
```

This provides a basic regression check that monitoring resources remain part of the chart.

It does not replace Prometheus Operator's server-side admission validation.

---

# 25. Helm Chart Signing

The Helm chart is signed as part of the Helm packaging/release implementation.

However, CI intentionally does **not** perform:

```bash
helm verify
```

The pipeline does not import the signing identity or manage private signing material.

Chart-signature verification is therefore outside the scope of this CI workflow.

This keeps signing concerns separate from normal source validation.

# 26. Terraform Validation

Terraform CI validates the configuration under:

```text
terraform/
```

without attempting to deploy anything.

The stage performs:

```text
terraform fmt
terraform init
terraform validate
```

It does not perform:

```text
terraform apply
```

---

# 27. Terraform Formatting

Formatting is checked using:

```bash
terraform fmt \
  -recursive \
  -check
```

The job fails when committed Terraform files do not follow standard Terraform formatting.

Developers can fix formatting locally with:

```bash
terraform fmt \
  -recursive
```

---

# 28. Terraform Initialization

CI initializes Terraform with:

```bash
terraform init \
  -backend=false
```

The objective is to initialize the required providers and modules without configuring or accessing a remote Terraform backend.

This is sufficient for static configuration validation.

---

# 29. Terraform Validate

After initialization:

```bash
terraform validate
```

checks the Terraform configuration for internal consistency.

This detects issues such as:

```text
invalid references
invalid arguments
incorrect provider configuration syntax
type mismatches
invalid resource configuration
```

---

# 30. Why Terraform Plan Is Not Run

The Terraform implementation deploys Helm packages to the local Kubernetes environment.

A standard GitHub-hosted runner does not have the local:

```text
what3words-exercise
```

k3d cluster.

Therefore the CI pipeline intentionally stops at:

```text
fmt
+
validate
```

and does not run:

```text
terraform plan
terraform apply
```

The separation is:

```text
CI
 │
 ├── terraform fmt
 ├── terraform init
 └── terraform validate


Local integration / deployment
 │
 ├── terraform plan
 └── terraform apply
```

This prevents CI from requiring local-cluster connectivity or deployment credentials.

---

# 31. ShellCheck

The repository contains shell scripts used for cluster management, deployment support, and resilience testing.

CI therefore performs static analysis using:

```text
ShellCheck
```

The workflow discovers shell scripts using:

```bash
find . \
  -type f \
  -name '*.sh' \
  -not -path './.git/*' \
  -print0
```

and sends them to:

```bash
shellcheck
```

This validates scripts such as the resilience tooling introduced in Extension D.

---

# 32. Why ShellCheck Is Included

Shell scripts are operational code.

A shell error in:

```text
load-test.sh
node-drain-test.sh
rolling-update-test.sh
```

could make resilience evidence unreliable even when the application itself is correct.

ShellCheck helps detect common problems such as:

```text
unsafe quoting
word splitting
incorrect variable handling
unused variables
problematic command substitution
shell portability issues
```

# 33. Final CI Status Job

The workflow contains a final:

```text
CI Success
```

job.

It depends on:

```text
Go Tests
Mock Sonar Scan
Docker Build
Helm Validation
Terraform Validation
ShellCheck
```

The dependency structure is:

```text
              Go Tests
              /      \
             /        \
            ▼          ▼
       Docker      Mock Sonar
            \          /
             \        /
              \      /

Helm ───────────────────┐
Terraform ───────────────┼──► CI Success
ShellCheck ──────────────┘
```

---

# 34. Why `if: always()` Is Used

The final job uses:

```yaml
if: always()
```

Without this, GitHub Actions may simply skip the final job when one of its dependencies fails.

Using `always()` allows the job to inspect every dependency result and print a concise summary.

Example:

```text
Go Tests:             success
Mock Sonar Scan:      success
Docker Build:         success
Helm Validation:      success
Terraform Validation: success
ShellCheck:           success
```

---

# 35. CI Success Criteria

The final job requires every dependency result to equal:

```text
success
```

If any result differs, the job exits with:

```text
exit 1
```

Therefore the overall required CI status becomes:

```text
All required jobs
        │
        ├── success
        ├── success
        ├── success
        ├── success
        ├── success
        └── success
                │
                ▼
           CI SUCCESS
```

Otherwise:

```text
Any required job
       │
       ▼
failure / cancelled / skipped
       │
       ▼
CI Success job
       │
       ▼
exit 1
```

# 36. CI Scope

The CI pipeline intentionally performs:

```text
✓ Go tests
✓ Go coverage
✓ Mock Sonar stage
✓ Docker build
✓ Helm lint
✓ Helm rendering
✓ Gateway API rendering checks
✓ Monitoring resource rendering checks
✓ Terraform formatting
✓ Terraform validation
✓ ShellCheck
```

It intentionally does not perform:

```text
✗ Docker image push
✗ Helm deployment
✗ Helm signature verification
✗ Terraform apply
✗ k3d cluster creation
✗ Envoy Gateway installation
✗ Prometheus installation
✗ node-drain test
✗ rolling-update resilience test
```

Those operations belong to deployment, release, or integration/resilience workflows rather than basic source CI.

The project separates fast CI checks from environment-dependent integration testing.

```text
                  Source Change
                       │
                       ▼
                       CI
                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
         Go          Helm       Terraform
        Tests       Render       Validate
          │
          ▼
       Docker
          │
          ▼
     Mock Sonar
                       │
                       ▼
                   CI Success
                       │
                       ▼
              Local Integration
                       │
            ┌──────────┴──────────┐
            ▼                     ▼
       Terraform Apply      Resilience Tests
                                  │
                         ┌────────┴────────┐
                         ▼                 ▼
                     Node Drain      Rolling Update
```

This keeps the normal feedback loop fast while retaining deeper operational tests separately.

# 39. Troubleshooting

## Go Tests Fail

Run locally:

```bash
cd app
go test -v ./...
```

For additional information:

```bash
go test \
  -race \
  -v \
  ./...
```

---

## Coverage Artifact Missing

Check that the test command contains:

```text
-coverprofile=coverage.out
```

and verify:

```bash
ls -lh app/coverage.out
```

The Sonar mock stage intentionally fails when the artifact does not exist.

---

## Docker Build Fails

Reproduce locally:

```bash
docker build \
  --progress=plain \
  -t greeter:ci \
  .
```

Because the CI image is not pushed, registry authentication is not required.

---

## Helm Validation Fails

Start with:

```bash
helm lint charts/greeter
```

Then render the complete manifest:

```bash
helm template \
  greeter \
  charts/greeter \
  --debug
```

Inspect the rendered YAML rather than only the original Helm template.

---

## ServiceMonitor Check Fails

Check:

```bash
helm template \
  greeter \
  charts/greeter \
  | grep -A30 'kind: ServiceMonitor'
```

Also verify:

```yaml
monitoring:
  enabled: true

  serviceMonitor:
    enabled: true
```

for the values used by the CI render.

---

## PrometheusRule Check Fails

Render:

```bash
helm template \
  greeter \
  charts/greeter \
  | grep -A50 'kind: PrometheusRule'
```

Confirm:

```yaml
monitoring:
  prometheusRule:
    enabled: true
```

and that at least one rule is configured.

---

## HTTPRoute Check Fails

Render:

```bash
helm template \
  greeter \
  charts/greeter \
  --set gateway.hostnames[0]=prod.greeter.local
```

Verify:

```text
kind: HTTPRoute
```

and:

```text
prod.greeter.local
```

exist in the generated manifest.

---

## Terraform Validate Fails

Run:

```bash
cd terraform

terraform init \
  -backend=false

terraform validate
```

If the failure is formatting-related:

```bash
terraform fmt \
  -recursive
```

then review and commit the formatting changes.

---

## ShellCheck Fails

Run against the specific script:

```bash
shellcheck \
  extensions/resilience/load-test.sh
```

ShellCheck outputs the rule identifier and location of each detected issue.

Fix the underlying shell problem rather than disabling rules globally unless there is a documented reason.

# 40. Design Decisions

## CI Does Not Deploy

The workflow validates source code and artifacts but does not mutate infrastructure.

This prevents a normal push from changing the local or shared Kubernetes environment.

---

## Tests Run Before Docker Build

Docker depends on:

```text
Go Tests
```

There is little value in spending time building the final container image when the application unit tests already fail.

The sequence is therefore:

```text
Go Tests
   │
   ▼
Docker Build
```

---

## Sonar Depends on Tests

The mock Sonar stage consumes:

```text
coverage.out
```

so it runs after the test job.

```text
Go Tests
   │
   ▼
Coverage Artifact
   │
   ▼
Mock Sonar
```

---

## Helm and Terraform Run Independently

Neither Helm rendering nor Terraform static validation requires the Go test results.

They can therefore execute in parallel.

This reduces overall CI duration.

---

## No Helm Signature Verification

Chart signing remains part of the Helm packaging implementation.

Signature verification is not repeated in this CI workflow.

This also avoids introducing GPG key-management concerns into a pipeline whose primary purpose is source validation.

---

## Mock Sonar Is Explicitly Identified

The pipeline does not claim that an actual SonarQube analysis occurred.

The job is explicitly named:

```text
Mock Sonar Scan
```

and its logs explain that it is a placeholder.

This preserves a clear distinction between:

```text
actual Go coverage
```

and:

```text
mocked Sonar findings
```

---

## No Terraform Apply

Terraform deployment requires access to the Kubernetes environment.

CI only verifies Terraform configuration.

Deployment remains an explicit operation through the Terraform workflow implemented in Step 4.

---

## No k3d Cluster in Basic CI

A temporary k3d cluster could be created inside GitHub Actions, but doing so would significantly increase pipeline complexity and execution time.

The current CI focuses on deterministic static/build validation.

Cluster-level behavior is demonstrated separately by the resilience extension.
