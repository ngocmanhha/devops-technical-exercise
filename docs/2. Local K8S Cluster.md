# Step 2 — Local Multi-Node Kubernetes Cluster

## Objective

Create a reproducible local Kubernetes cluster using **k3d** with at least **two worker nodes**.

The cluster runs entirely on the local machine using Docker and does not require any cloud account, external Kubernetes service, or paid infrastructure.

The cluster name used throughout this exercise is:

```text
what3words-exercise
```

---

## 1. Why k3d

[k3d](https://k3d.io/) is used to create the local Kubernetes environment.

k3d runs [k3s](https://k3s.io/) inside Docker containers, providing a lightweight Kubernetes environment suitable for local development and testing.

It was selected for this exercise because it provides:

- Fast local cluster creation
- Multi-node Kubernetes support
- Low resource overhead
- Docker-based execution
- ARM64 support for Apple Silicon
- AMD64/x86_64 support
- Simple local container image import
- Reproducible cluster configuration
- No cloud infrastructure dependency

The main trade-off is that k3d runs **k3s** rather than a full upstream Kubernetes distribution.

This is acceptable for this exercise because the application will use standard Kubernetes resources and does not depend on k3s-specific functionality.

---

## 2. Cluster Architecture

The local cluster consists of:

- **1 server/control-plane node**
- **2 agent/worker nodes**

Architecture:

```text
                  Local Machine
               macOS / Linux / ARM64
                        │
                        ▼
                     Docker
                        │
                        ▼
              ┌───────────────────┐
              │       k3d         │
              │                   │
              │ what3words-       │
              │ exercise          │
              └─────────┬─────────┘
                        │
           ┌────────────┼────────────┐
           │            │            │
           ▼            ▼            ▼
     ┌───────────┐ ┌───────────┐ ┌───────────┐
     │ Server 0  │ │  Agent 0  │ │  Agent 1  │
     │           │ │           │ │           │
     │ Control   │ │  Worker   │ │  Worker   │
     │ Plane     │ │  Node     │ │  Node     │
     └───────────┘ └───────────┘ └───────────┘
```

This satisfies the exercise requirement for a local multi-node Kubernetes cluster with at least two worker nodes.

The two worker nodes will also allow later steps to demonstrate application availability when one worker node becomes unavailable.

## 8. Architecture Verification

The cluster should work on both ARM64 and AMD64 development machines.

Check the architecture of each Kubernetes node:

```bash
kubectl get nodes \
  -o custom-columns='NAME:.metadata.name,ARCH:.status.nodeInfo.architecture,OS:.status.nodeInfo.operatingSystem'
```

On an Apple Silicon machine such as an M3, the expected architecture is:

```text
arm64
```

On an Intel or AMD machine, the expected architecture is typically:

```text
amd64
```

The cluster configuration does not force a specific CPU architecture, allowing Docker and k3d to use the native architecture of the host.

This complements the multi-architecture container build implemented in Step 1.

## 9. Import the Local Application Image

The application image created in Step 1 can be imported directly into the k3d cluster.

Build the image:

```bash
docker build -t greeter:local .
```

Import it into the cluster:

```bash
k3d image import greeter:local \
  --cluster what3words-exercise
```

This avoids requiring an external container registry for local development.

The Kubernetes deployment should therefore use:

```yaml
image:
  repository: greeter
  tag: local
  pullPolicy: IfNotPresent
```

`IfNotPresent` is important because the image has already been imported into the local k3d nodes.

Using `Always` would cause Kubernetes to attempt to pull the image from an external registry.

## 11. Worker Node Availability

The two worker nodes are required not only to satisfy the cluster topology requirement but also to support the availability requirements of the application.

Later, application replicas will be distributed across the worker nodes:

```text
                Kubernetes Service
                       │
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
        ┌───────────┐     ┌───────────┐
        │  Agent 0  │     │  Agent 1  │
        │           │     │           │
        │ Greeter   │     │ Greeter   │
        │ Pod       │     │ Pod       │
        └───────────┘     └───────────┘
```

If one worker node becomes unavailable:

```text
        Agent 0                  Agent 1
           │                        │
           X                        ▼
       unavailable              Greeter Pod
                                    │
                                    ▼
                              Service remains
                                 available
```

The actual workload distribution and availability controls will be implemented in the Kubernetes packaging step.

## 12. Test Node Failure

Once the application is deployed in a later step, a worker node can be drained to test resilience.

For example:

```bash
kubectl drain k3d-what3words-exercise-agent-0 \
  --ignore-daemonsets \
  --delete-emptydir-data
```

Check the remaining nodes:

```bash
kubectl get nodes
```

Check application pod placement:

```bash
kubectl get pods -o wide
```

After testing, restore the node:

```bash
kubectl uncordon k3d-what3words-exercise-agent-0
```

This test will later be used to demonstrate whether the application remains available during the loss of a worker node.

## 15. Design Decisions

### k3d Instead of a Cloud Kubernetes Service

The exercise requires everything to run locally.

Using k3d avoids introducing unnecessary dependencies such as:

- AWS EKS
- Google Kubernetes Engine
- Azure Kubernetes Service
- Cloud credentials
- Cloud networking
- Cloud container registries
- Infrastructure costs

The resulting environment remains fully reproducible on a developer machine.

### Two Worker Nodes

Two worker nodes are intentionally provisioned because the application must later remain available if one node is lost.

This provides a realistic environment for testing:

- Replica distribution
- Pod rescheduling
- Node failure
- Pod disruption
- Rolling updates
- Graceful termination

### One Control Plane

Only one control-plane/server node is used.

Control-plane high availability is outside the scope of this exercise. The objective is to demonstrate application-level availability across worker-node failure rather than build a production-grade Kubernetes control plane.

A production environment would normally use multiple control-plane nodes managed across separate failure domains.

### Native Host Architecture

No architecture is hard-coded into the cluster.

Apple Silicon machines can therefore run ARM64 nodes natively, while AMD64 hosts can run AMD64 nodes.

This avoids unnecessary CPU emulation and improves local performance.

### Local Image Import

The application image is imported directly into k3d rather than pushed to an external registry.

This keeps the exercise:

- Fully local
- Faster to reproduce
- Independent of registry credentials
- Free from external infrastructure dependencies

For a production environment, images would instead be built by CI and pushed to a managed container registry.
