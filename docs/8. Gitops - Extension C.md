# Extension C — GitOps with Argo CD

## Objective

Implement GitOps for the Greeter service using **Argo CD**.

The objective of this extension is to demonstrate that Kubernetes application state can be continuously reconciled from Git.

The deployment flow is:

```text
Git change
    │
    ▼
git commit / push
    │
    ▼
Argo CD detects new revision
    │
    ▼
Automatic reconciliation
    │
    ▼
Helm chart rendered
    │
    ▼
Kubernetes updated
```

This demonstrates the GitOps requirement that a change committed to the repository can result in a corresponding change in the cluster.

---

# 1. Why Argo CD

Both **Argo CD** and **FluxCD** are valid GitOps solutions for Kubernetes.

For this exercise, **Argo CD was selected because it provides a simpler demonstration and evaluation experience**.

The main considerations were:

| Consideration | Argo CD | FluxCD |
|---|---|---|
| GitOps reconciliation | Yes | Yes |
| Helm support | Yes | Yes |
| Automatic synchronization | Yes | Yes |
| Drift detection | Yes | Yes |
| Self-healing | Yes | Yes |
| Built-in Web UI | Yes | No built-in equivalent |
| Easy visual verification | Strong | Primarily CLI/resources |
| Interview demonstration | Simple | More controller-oriented |

The main reason for choosing Argo CD is the built-in UI and clear application health/synchronization model.

During an interview, the GitOps behavior can be demonstrated visually:

```text
Git revision
      │
      ▼
OutOfSync
      │
      ▼
Sync
      │
      ▼
Synced
+
Healthy
```

This makes it straightforward to demonstrate:

- Git revision tracking
- synchronization status
- resource health
- deployment history
- Kubernetes resources
- drift detection
- automatic reconciliation

FluxCD would also satisfy the technical requirements, but Argo CD provides a more convenient and observable demonstration for a small take-home exercise.

This is therefore an evaluation/usability decision rather than a claim that Argo CD is technically superior to FluxCD.

# 2. Architecture

The GitOps architecture is:

```text
                     Git Repository
                           │
                           │ poll
                           ▼
                        Argo CD
                           │
                           │ Helm rendering
                           ▼
                    charts/greeter
                           │
                ┌──────────┴──────────┐
                │                     │
                ▼                     ▼
           greeter-dev           greeter-prod
                │                     │
                ▼                     ▼
           Dev workload          Prod workload
                │                     │
                └──────────┬──────────┘
                           │
                           ▼
                     Envoy Gateway
```

The existing Helm chart remains the deployment package:

```text
charts/greeter
```

Argo CD becomes responsible for continuously reconciling the desired state from Git.

# 4. Install Argo CD

Create the namespace:

```bash
kubectl create namespace argocd
```

Add the Argo Helm repository:

```bash
helm repo add argo \
  https://argoproj.github.io/argo-helm
```

Update repositories:

```bash
helm repo update
```

Install Argo CD:

```bash
helm upgrade \
  --install \
  argocd \
  argo/argo-cd \
  --namespace argocd \
  --wait \
  --timeout 5m
```

# 8. Environment-Specific Helm Values

The base configuration remains in:

```text
charts/greeter/values.yaml
```

Environment-specific values are supplied directly through the GitOps configuration using Helm `valuesObject`.

Conceptually:

```text
charts/greeter/values.yaml
          │
          │ base configuration
          ▼
    environment overrides
          │
          ▼
      valuesObject
          │
          ▼
       Helm render
          │
          ▼
   Kubernetes manifests
```

This approach was selected instead of maintaining external value files such as:

```text
gitops/values/dev.yaml
gitops/values/prod.yaml
```

because the number of environment differences is small.

It also avoids unnecessary value-file path resolution between the GitOps configuration and the Helm chart.

---

# 9. Environment Separation

Two namespaces are maintained:

```text
greeter-dev
greeter-prod
```

Typical differences include:

```text
DEV                         PROD
────────────────────────────────────────
1 replica                   2 replicas

dev configuration           prod configuration

dev.greeter.local           prod.greeter.local
```

Common configuration remains in:

```text
charts/greeter/values.yaml
```

Only environment-specific differences need to be overridden by GitOps.

# 10. Automatic Synchronization

Automatic synchronization is enabled so that Argo CD can reconcile Git changes without requiring a manual deployment.

The lifecycle is:

```text
Desired state in Git
        │
        ▼
     Argo CD
        │
        │ compare
        ▼
Actual cluster state
        │
        ├── identical
        │      │
        │      ▼
        │    Synced
        │
        └── different
               │
               ▼
           OutOfSync
               │
               ▼
        automatic reconciliation
               │
               ▼
             Synced
```

This removes the need to run:

```bash
helm upgrade
```

after every application configuration change.

---

# 11. Self-Healing

Self-healing allows Argo CD to detect manual changes made directly to Kubernetes resources and restore the Git-defined state.

For example:

```text
Git desired state

replicas = 1
      │
      ▼
Kubernetes manually changed

replicas = 3
      │
      ▼
Argo CD detects drift
      │
      ▼
Automatic reconciliation
      │
      ▼
replicas = 1
```

This demonstrates an important GitOps principle:

> Git represents the desired application state.

Manual cluster changes should not permanently override that state.

---

# 12. Automatic Pruning

Automatic pruning removes Kubernetes resources that no longer exist in the desired Git configuration.

For example:

```text
Resource exists in Git
        │
        ▼
Resource exists in Kubernetes
```

After the resource is removed from Git:

```text
Resource removed from Git
        │
        ▼
Argo CD detects difference
        │
        ▼
Resource removed from Kubernetes
```

This prevents obsolete resources from remaining in the cluster after they have been removed from the deployment definition.

The key validation for this extension is demonstrating that a Git commit results in a cluster change.


Argo CD detects the new repository revision and reconciles the change.

# 19. Force Repository Refresh

During a demonstration, waiting for the normal repository polling interval is unnecessary.

A hard refresh can be requested:

```bash
kubectl annotate application \
  greeter-dev \
  -n argocd \
  argocd.argoproj.io/refresh=hard \
  --overwrite
```

Then check:

```bash
kubectl get applications \
  -n argocd
```

This is useful during testing or an interview demonstration.

Normal GitOps operation does not require manually forcing refreshes.

# 22. Terraform and GitOps Responsibilities

Terraform was previously used to demonstrate Helm deployment for both environments.

Once GitOps is introduced, avoid having Terraform and Argo CD continuously manage the same Greeter Kubernetes resources.

Avoid:

```text
              Greeter resources
                 ▲       ▲
                 │       │
            Terraform   Argo CD
```

Two reconcilers managing the same resources can cause ownership conflicts and configuration drift.

The preferred responsibility model is:

```text
             Platform / Bootstrap
                     │
                     ▼
                  Terraform
                     │
                     ▼
             Cluster prerequisites


               Application
                   │
                   ▼
                 Git
                   │
                   ▼
                Argo CD
                   │
                   ▼
             charts/greeter
                   │
              ┌────┴────┐
              ▼         ▼
             dev       prod
```

Terraform demonstrates infrastructure/deployment automation, while GitOps demonstrates continuous application reconciliation.

# 23. Repository Access

Argo CD runs inside Kubernetes and therefore cannot directly watch the local project directory on the workstation.

For example, it cannot directly use:

```text
/Users/user/what3words-exercise
```

The GitOps relationship is:

```text
Local working tree
        │
        ▼
    git commit
        │
        ▼
 Git repository
        │
        ▼
     Argo CD
        │
        ▼
    Kubernetes
```

Repository credentials should never be committed to the exercise repository.

Do not store:

```text
GitHub PAT
API tokens
repository passwords
SSH private keys
```

inside Git.

For a public repository, Argo CD can use anonymous read access.

For private repositories, authentication should be provided separately through the runtime environment.

# 24. Troubleshooting

## GitOps State Is OutOfSync

Check:

```bash
kubectl get applications \
  -n argocd
```

Then inspect the detailed status:

```bash
kubectl describe application \
  greeter-dev \
  -n argocd
```

A refresh can be requested with:

```bash
kubectl annotate application \
  greeter-dev \
  -n argocd \
  argocd.argoproj.io/refresh=hard \
  --overwrite
```

---

## Workload Is Degraded

Check:

```bash
kubectl get pods \
  -n greeter-dev
```

Inspect the affected pod:

```bash
kubectl describe pod \
  -n greeter-dev \
  <pod-name>
```

Check recent events:

```bash
kubectl get events \
  -n greeter-dev \
  --sort-by='.lastTimestamp'
```

Common causes include:

```text
ImagePullBackOff
readiness probe failure
invalid scheduling constraints
missing CRDs
invalid configuration
```

---

## Helm Rendering Fails

Validate locally:

```bash
helm lint \
  charts/greeter
```

Then:

```bash
helm template \
  greeter \
  charts/greeter
```

If local Helm rendering succeeds but Argo CD fails, inspect the Argo CD reconciliation status and repository-server logs.

---

## Repository Cannot Be Read

Inspect:

```bash
kubectl describe application \
  greeter-dev \
  -n argocd
```

Check repo-server:

```bash
kubectl logs \
  -n argocd \
  deployment/argocd-repo-server
```

Verify:

```text
repository URL
repository accessibility
target branch
network connectivity
authentication, if required
```

---

## Git Change Is Not Detected

First confirm the commit was pushed:

```bash
git log \
  -1 \
  --oneline
```

Check the remote branch:

```bash
git status
```

Then force an Argo CD refresh:

```bash
kubectl annotate application \
  greeter-dev \
  -n argocd \
  argocd.argoproj.io/refresh=hard \
  --overwrite
```

Watch:

```bash
kubectl get applications \
  -n argocd \
  -w
```

# 25. Validation Checklist

The GitOps implementation is complete when:

```text
✓ Argo CD is installed
✓ Argo CD controllers are healthy
✓ Existing charts/greeter package is reused
✓ Dev and prod are independently configured
✓ Environment-specific Helm values are defined declaratively
✓ Automatic synchronization is enabled
✓ Pruning is enabled
✓ Self-healing is enabled
✓ Dev workload is Healthy
✓ Prod workload is Healthy
✓ HTTPRoutes are available
✓ Envoy Gateway routes to both environments
✓ Git commit can change cluster state
✓ No manual Helm upgrade is needed after Git changes
```

Optional additional evidence:

```text
✓ Manual cluster drift is automatically corrected
✓ Deleted desired-state resources are automatically pruned
```

# 26. Result

The final GitOps model is:

```text
                       Git
                        │
                        │ desired state
                        ▼
                     Argo CD
                        │
                        │ reconciliation
                        ▼
                 charts/greeter
                        │
                        │ Helm
                        ▼
             Kubernetes resources
                        │
               ┌────────┴────────┐
               ▼                 ▼
          greeter-dev       greeter-prod
               │                 │
               └────────┬────────┘
                        ▼
                  Envoy Gateway
```

The core behavior demonstrated is:

```text
Git change
    ↓
Commit
    ↓
Push
    ↓
Argo CD detects revision
    ↓
Automatic reconciliation
    ↓
Kubernetes changes
    ↓
Synced + Healthy
```

Argo CD was chosen over FluxCD primarily because its built-in UI and explicit **Synced / OutOfSync / Healthy / Degraded** model make the GitOps behavior easier for an evaluator to inspect and verify during this exercise, while both tools are technically capable of satisfying the GitOps requirement.
