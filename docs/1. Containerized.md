# Step 1 — Containerize the Go Service

## Objective

Package the provided Go HTTP service as a portable container image that can run consistently across different development machines and CPU architectures.

The solution supports:

- macOS with Apple Silicon (M1/M2/M3/M4)
- Linux ARM64
- Linux AMD64/x86_64
- Intel-based macOS through Docker
- Local Docker Compose
- Local Kubernetes clusters used in later steps

No application code is modified as part of this step.

---

## 1. Application Overview

The application source is located under:

```text
app/
```

The service listens on port `8080` by default and exposes the following endpoints:

| Endpoint | Purpose |
|---|---|
| `GET /` | Returns the configured greeting |
| `GET /healthz` | Liveness endpoint |
| `GET /readyz` | Readiness endpoint |
| `GET /version` | Returns the configured application version |
| `GET /metrics` | Exposes Prometheus metrics |
| `GET /boom` | Intentionally returns HTTP 500 |
| `GET /work?ms=N` | Simulates a long-running request |

### Configuration

The application is configured entirely through environment variables.

| Variable | Default | Description |
|---|---|---|
| `GREETING_NAME` | Required | Greeting name. The application exits if missing or empty. |
| `PORT` | `8080` | HTTP listening port |
| `VERSION` | `dev` | Application version |
| `WARMUP_SECONDS` | `30` | Readiness warm-up duration |
| `SHUTDOWN_DELAY_SECONDS` | `10` | Delay after receiving `SIGTERM` |
| `DRAIN_TIMEOUT_SECONDS` | `20` | Maximum time for in-flight requests to finish |

`GREETING_NAME` is intentionally not embedded into the image because it needs to be configurable per environment without rebuilding the image.

## 2. Container Design

A multi-stage Docker build is used:

```text
Go Source
    │
    ▼
┌───────────────────────┐
│     Builder Stage     │
│                       │
│  go mod download      │
│  go test ./...        │
│  go build             │
└───────────┬───────────┘
            │
            │ Static binary
            ▼
┌───────────────────────┐
│     Runtime Stage     │
│                       │
│  greeter binary       │
│  non-root user        │
└───────────┬───────────┘
            │
            ▼
         Port 8080
```

This separates build-time dependencies from runtime dependencies.

The final runtime image does not need to contain:

- Go compiler
- Go modules
- Application source code
- Build tools

This reduces image size and runtime attack surface.

## 4. Cross-Platform Build

Docker BuildKit provides the following platform arguments:

```dockerfile
ARG TARGETOS
ARG TARGETARCH
```

The Go application is compiled with:

```text
CGO_ENABLED=0
GOOS=<target OS>
GOARCH=<target architecture>
```

Using `CGO_ENABLED=0` produces a portable Go binary and avoids host-specific cgo issues.

Although the development machine may be macOS, the target container is Linux because the Kubernetes environment runs Linux containers.

Typical targets are:

```text
macOS M3
   │
   ├── linux/arm64
   │
   └── linux/amd64
   │
   ▼
Docker / Kubernetes
```

This allows the same Dockerfile to work on both Apple Silicon and conventional AMD64 machines.

## 5. Build the Image

### Apple Silicon — M1/M2/M3/M4

```bash
docker build \
  --platform linux/arm64 \
  -t greeter:exercise \
  .
```

### AMD64 / x86_64

```bash
docker build \
  --platform linux/amd64 \
  -t greeter:exercise \
  .
```

### Multi-Architecture Build

Docker Buildx can build both architectures:

```bash
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t greeter:latest \
  .
```

A container registry is intentionally not introduced at this stage because the exercise runs entirely locally.

## 6. Run the Container

`GREETING_NAME` must be provided because it is required by the application.

```bash
docker run --rm \
  -p 8080:8080 \
  -e GREETING_NAME="Exercise" \
  -e VERSION="exercise" \
  -e WARMUP_SECONDS=5 \
  greeter:exercise
```

The application is then accessible at:

```text
http://localhost:8080
```

## 11. Graceful Shutdown

The application implements deliberate graceful-shutdown behavior.

When the process receives `SIGTERM`:

1. `/readyz` immediately starts returning HTTP `503`.
2. The application continues serving traffic.
3. It waits for `SHUTDOWN_DELAY_SECONDS`.
4. It stops accepting new connections.
5. It waits up to `DRAIN_TIMEOUT_SECONDS` for in-flight requests.
6. The process exits normally.

With the default configuration:

```text
SHUTDOWN_DELAY_SECONDS = 10 seconds
DRAIN_TIMEOUT_SECONDS  = 20 seconds
----------------------------------
Maximum expected       = ~30 seconds
```

Docker Compose therefore uses:

```yaml
stop_grace_period: 40s
```

This provides sufficient time for the application to complete its normal shutdown sequence before Docker forcibly terminates it.

The same behavior will need to be accounted for later in the Kubernetes `terminationGracePeriodSeconds` and readiness configuration.

## 12. Design Decisions

### Multi-Stage Build

Build dependencies are separated from runtime dependencies.

This keeps the final image smaller and avoids shipping unnecessary development tools.

### Static Go Binary

The application is compiled using:

```text
CGO_ENABLED=0
```

Benefits include:

- Better portability
- No runtime dependency on libc
- Avoids host-specific cgo issues
- Works well across container environments

### Multi-Architecture Support

The Dockerfile supports:

```text
linux/arm64
linux/amd64
```

This allows development on Apple Silicon while still supporting conventional AMD64 Kubernetes environments.

### Non-Root Runtime

The service runs using an unprivileged user:

```dockerfile
USER 10001:10001
```

Running applications as non-root reduces the impact of a potential container compromise.

### Runtime Configuration

Environment-specific values are supplied at runtime:

```text
GREETING_NAME
VERSION
WARMUP_SECONDS
SHUTDOWN_DELAY_SECONDS
DRAIN_TIMEOUT_SECONDS
```

They are not embedded into the image.

This means the same immutable image can later be used for:

```text
dev
 │
 ├── GREETING_NAME=Dev
 └── replicas=N

prod
 │
 ├── GREETING_NAME=Production
 └── replicas=N
```

without rebuilding the application.

### Docker Compose Scope

Docker Compose is deliberately used only for:

- Local development
- Image verification
- Testing application configuration
- Testing startup/shutdown behavior

The actual deployment will be performed through Kubernetes and Terraform.
